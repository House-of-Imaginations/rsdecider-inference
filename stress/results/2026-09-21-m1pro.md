# Stress results — 2026-09-21, Apple M1 Pro

Host: M1 Pro, 10 cores (8P + 2E), 16 GB, macOS. Server: `target/release/rsdecider serve --config stress/rsdecider.stress.toml`
Models: real fp32 ONNX exports (`english` 1.6 GB, `multilingual` 1.2 GB), CPU execution provider, no Redis.
Each k6 scenario ramps to the listed arrival rate over 2 min. `http_req_failed` counts 529 as failed. The check that matters is
"status is 200 or 529": it passed 100% in every run.

## Run 3 — tokenize queue (`tokenize` scenario, build de34af8 + knobs)

Unique ~90k-char states (they tokenize in ~18 ms and truncate to 1,536 tokens, about 2.6 s of inference per request).
`knobs.tokenize_queue = 112`, one tokenize thread.

| Rate | Requests | 200 | 529 (tokenize queue / model queue) | 504 | 529 p50 | Peak RSS |
|---|---|---|---|---|---|---|
| 40 req/s | 4,859 | 6 | 4,794 (0 / 4,794) | 59 (1.2%) | ~20 ms | 2.5 GB |
| 200 req/s | 24,059 | 64 | 23,941 (15,750 / 8,191) | 54 (0.2%) | 2 ms | 2.1 GB |

- At 40 req/s the model is the bottleneck, so the tokenize queue never fills and the model queue does the shedding.
- At 200 req/s (over the ~55 req/s one tokenize thread can take) the tokenize queue sheds two-thirds of the load up front,
  and memory stays bounded.
- **Open issue:** a small share of accepted long-input requests still exceed the 10 s deadline (504). Short-input runs
  (run 2) had none. The likely cause is that admission estimates cost per item, not per token, while k6 competes with
  inference for the same CPU; this isn't proven yet.

## Interpretation

- **Capacity (cold, fp32 on CPU):** English handles about 10 items/s, roughly 3 req/s at 3 questions each. Multilingual handles about 4 items/s.
  Cold p99 stays under 600 ms while load is below that knee.
- **Past the knee the server sheds, it does not queue.** Excess load gets fast 529s with Retry-After (p50 about 1 ms).
  Accepted requests finish inside the 10 s deadline. No requests timed out, errored, or leaked pending permits.
- **Cache hits are effectively free:** about 2000 req/s at p99 1.4 ms, bounded by k6 and the host rather than by the server.
- **Batch starvation:** all-or-nothing admission of 24 items loses to single requests under contention. This is a known limit; see the follow-ups below.
- **Most room to grow:** use an int8-quantized export, or CoreML/GPU execution providers. fp32 CPU inference is the bottleneck, not the Rust engine.
