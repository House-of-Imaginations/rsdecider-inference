# Stress results — 2026-09-21, Apple M1 Pro

Host: M1 Pro, 10 cores (8P + 2E), 16 GB, macOS. Server: `target/release/rsdecider serve --config stress/rsdecider.stress.toml`
Models: real fp32 ONNX exports (`english` 1.6 GB, `multilingual` 1.2 GB), CPU execution provider, no Redis.
Each k6 scenario ramps to the listed arrival rate over 2 min. `http_req_failed` counts 529 as failed. The check that matters is
"status is 200 or 529": it passed 100% in every run.

## Run 5 — MLX backend (build f1b905c)

One release binary (`cargo build --release --features mlx`) served both backends from the same
`models/english` / `models/multilingual` folders (fp32 `model.onnx` for ORT, `mlx.safetensors` + `mlx.json` for MLX);
scratch configs, both copies of `stress/rsdecider.stress.toml` (both `workers = 1`, `max_pending` 48/64), differed
only in `execution_provider` (the MLX one also spelled out the default `mlx_dtype = "fp16"`), on ports 3700/9700
(3000/3001/9000 belong to an idle OrbStack/Docker compose stack left running per instructions — not touched, and idle
throughout). k6 used the fixed iteration id (`exec.scenario.iterationInTest` instead of the buggy
`__ITER + __VU * 1e6`, which degenerates `cold`'s language mix to almost all-English); that fix lands with PR #5
(`fix/admission-headroom`), so until it merges this branch's `stress/scenario.js` still sends mostly English on
`cold`. Each run here got a mixed English/Vietnamese/Spanish state distribution and a unique `-e SEED` so no run reused another's cache. Default ramp (2 min) / hold
(1 min) throughout; fresh server per run, killed and port-checked free before the next.

**MLX cold capacity search** (raising `cold`'s rate until 529s appear): 0% shed through 3, 6, 10, 15 and 20 req/s
(p99 stayed 79–108 ms; peak `footprint` 2.87 GB at 6, 3.17–3.18 GB at 10–20, 4.67 GB at 30, 4.97 GB at 40); first shedding at **25 req/s (0.13%, 4/3,059)**; clearly shedding at 30 (8.0%, 294/3,659) and
40 (21.9%, 1,066/4,859). So MLX's cold knee sits around **25–30 req/s**, roughly **8–10×** ORT CPU fp32's ~3 req/s
cold capacity (Run 4/README) on the same host and models. That knee was found with the stress config's `max_pending`
48/64, sized for ORT: it is a lower bound set by queue size (admission sheds once the queue is full), not a measured
GPU saturation point, so don't cite it as MLX's capacity. At the MLX knee rate (25 req/s), ORT sheds 71% (2,182/3,059)
with accepted p99 already at 9.35 s — right against the 10 s deadline — while MLX sheds essentially nothing.

**Noise and caveats (read before citing these numbers):**
- **Single runs, not repeats.** Every cell above is one k6 run at one rate; no run was repeated to check variance.
  Treat differences of less than ~2× as noise; the ORT-vs-MLX gaps here (4–9× on latency, 6× on overload throughput,
  8–10× on cold capacity) are far past that bar, but exact figures (e.g. "25–30 req/s knee", itself a `max_pending`-
  bound lower bound) shouldn't be read as precise.
- **Shared host.** An OrbStack/Docker compose stack (Redis + whatever else) was running idle on 3000/3001/9000 the
  whole time — not stopped, per instructions — and this is a desktop, so the GPU MLX used is the same one driving
  the display and any other apps, not a dedicated accelerator.
- **1-min load average was above ~4 immediately before four runs**, most likely residual CPU from the just-killed
  previous server/k6 process rather than independent host load: mlx-cold3 (6.30), cold@25 ORT (7.07), overload@100
  ORT (8.35), overload@100 MLX (8.60). All other runs started at 1-min load ≤ 3.6.
- **`ps -o rss` badly undercounts MLX's real memory use** — e.g. overload@100 shows MLX at 515 MB by `ps` vs ORT at
  3.93 GB, which reads like a 7–8× memory win. It isn't: macOS `footprint` (physical footprint, includes
  GPU/unified-memory-resident allocations that `ps` misses for MLX) shows MLX at 5.03/5.57 GB on the two paired runs
  (cold@25, overload@100), actually *higher* than ORT's 3.11/4.33 GB on the same runs — consistent with fp16 weights
  plus Metal working buffers, not a memory-frugal backend. Across all sampled MLX runs the footprint grows with load,
  from ~2.9 GB (cold@6) to ~5.6 GB (overload@100); plan ~5–6 GB for both models under load. The two cold@3 rows only have `ps` numbers (footprint sampling
  was added afterward) and should not be used for a memory comparison.
- **MLX numbers are Apple Silicon only** — the `mlx` feature doesn't compile anywhere else (`compile_error!` outside
  `macos` + `aarch64`), so none of this generalizes to Linux/x86/CUDA deployments.

## Run 4 — bucketing, token-aware admission, prefix tokenization (build 5cd0ec7 vs main 721eaad)

Same host and stress config, fp32, a fresh server per run. `padded / real` is `rsdecider_padded_tokens_total ÷
rsdecider_real_tokens_total` (the extra work padding costs).

| Scenario | Build | 200 | 529 | 504 | Latency (200s) | Peak RSS |
|---|---|---|---|---|---|---|
| overload @ 100 | main 721eaad | 1,106 | 10,953 | 0 | p99 7.05 s | 2.7 GB |
| overload @ 100 | 5cd0ec7 | 1,068 | 10,991 | 0 | p99 7.21 s | 2.28 GB |
| cold @ 3 | 5cd0ec7 | 419 / 419 | 0 | 0 | p50 287 ms, p95 345 ms, p99 518 ms | 2.73 GB |
| tokenize @ 40 | 5cd0ec7 | 41 | 4,797 | 21 | — | 2.2 GB |
| tokenize @ 200 | 5cd0ec7 | 39 | 23,986 | 34 | p99 385 ms | 2.23 GB |

- **Padding:** overload runs at 5.5% extra (English 98,727 / 93,584) and 6% (multilingual 79,621 / 75,044); cold@3 at
  5.5% (64,197 / 60,845). Long-input runs pad 0%: every state truncates to the same cap.
- **Throughput is unchanged** on overload (1,068 vs 1,106 served, within run-to-run noise); peak RSS dropped ~0.4 GB.
- **A regression found and fixed on the way:** the first bucketing version filled batches with the *closest* lengths,
  so newer same-type questions overtook a request's sibling questions and 57 accepted requests hit 504 on overload.
  5cd0ec7 fills in arrival order within 2× of the oldest item's length; 504s went back to 0.
- **Prefix tokenization:** at 200 req/s the tokenize queue shed 20 requests instead of 15,750 in run 3. Tokenizing a
  90k-char state is now cheap, so nearly all shedding moves to the model queue.
- **504 verdict:** token-aware admission reduced long-input 504s (run 3 on main: 59 at 40 req/s, 54 at 200 req/s)
  but did not remove them: 21 and 34 here, 0.4–0.5% of accepted requests. With 0% padding and per-token costing,
  the rest is likely CPU contention with k6 on the same host making the EMA lag; this is not proven.

## Run 3 — tokenize queue (`tokenize` scenario, build de34af8 + knobs)

Unique ~90k-char states (they tokenize in ~18 ms and truncate to the model cap: 512 tokens English, 1,024 multilingual).
`knobs.tokenize_queue = 112`, one tokenize thread.

| Rate | Requests | 200 | 529 (tokenize queue / model queue) | 504 | 529 p50 | Peak RSS |
|---|---|---|---|---|---|---|
| 40 req/s | 4,859 | 6 | 4,794 (0 / 4,794) | 59 (1.2%) | ~20 ms | 2.5 GB |
| 200 req/s | 24,059 | 64 | 23,941 (15,750 / 8,191) | 54 (0.2%) | 2 ms | 2.1 GB |

- At 40 req/s the model is the bottleneck, so the tokenize queue never fills and the model queue does the shedding.
- At 200 req/s (over the ~55 req/s one tokenize thread can take) the tokenize queue sheds two-thirds of the load up front,
  and memory stays bounded.
- **Open issue:** a small share of accepted long-input requests still exceed the 10 s deadline (504). Short-input runs
  (run 2) had none. The likely cause is that admission estimates cost per item, not per token, while k6 competes with
  inference for the same CPU; this isn't proven yet.

## Interpretation

- **Capacity (cold, fp32 on CPU):** English handles about 10 items/s, roughly 3 req/s at 3 questions each. Multilingual handles about 4 items/s.
  Cold p99 stays under 600 ms while load is below that knee.
- **Past the knee the server sheds, it does not queue.** Excess load gets fast 529s with Retry-After (p50 about 1 ms).
  Accepted requests finish inside the 10 s deadline. No requests timed out, errored, or leaked pending permits.
- **Cache hits are effectively free:** about 2000 req/s at p99 1.4 ms, bounded by k6 and the host rather than by the server.
- **Batch starvation:** all-or-nothing admission of 24 items loses to single requests under contention. This is a known limit; see the follow-ups below.
- **Most room to grow:** use an int8-quantized export, or CoreML/GPU execution providers. fp32 CPU inference is the bottleneck, not the Rust engine.
